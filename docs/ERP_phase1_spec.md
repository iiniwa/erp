## 1. システム概要

### 1.1 実装スコープ（第一フェーズ）
- ログイン機能（ID/パスワード認証、社員証QRコード認証）
- 従業員情報管理
- アドレス帳機能
- 権限管理（機能単位のRBAC）
- フロントエンドのPWA対応・レスポンシブ対応（詳細は「11. フロントエンド実装方針」参照）
- ローカル開発環境の整備（詳細は「12. 開発環境・リポジトリ構成」参照）
- Claude Codeへの実装引き継ぎ・Issue管理（詳細は「14. Claude Code実装引き継ぎ方針」参照）

### 1.2 アーキテクチャ
- **フロントエンド**: Next.js + Tailwind CSS、PWA対応
- **バックエンド**: Ruby on Rails（分離型で確定）
- **DB**: MariaDB
- **ファイルストレージ**: SFTPGo（詳細は「9. ファイルストレージ構成」参照）
- **認証方式**: 分離型
  - Next.js（NextAuth）が認証・セッション管理を担当
  - Next.js側API Route（BFF層）がセッション検証後、内部シークレット/署名付きトークンでバックエンドAPIへリクエストを中継
  - バックエンドAPI側でも権限チェックを必須実装（多重防御。将来の外部公開を見据える）
- **インフラ**: Proxmox上のDockerコンテナ、Cloudflare Tunnel経由で公開、Valuedomain管理ドメインのサブドメイン使用
- **リポジトリ構成**: 単一リポジトリ内でフロントエンド／バックエンドのディレクトリを分割するモノレポ方式（詳細は「12. 開発環境・リポジトリ構成」参照）
- **保存期間/削除方針**: 論理削除ベース。法定保存義務のある帳票データ（第二フェーズ以降）は法定期間経過後に物理削除する二段階方式（本フェーズのテーブルは対象外）

## 2. ID採番方式（共通ルール）

```
TTYYMMNNN
TT: 種別コード（1〜2桁）
YY: 年（下2桁）
MM: 月（2桁）
NNN: 通し番号（3桁、月次リセット）
```

| テーブル | TT |
|---|---|
| t.users | 9 |
| t.address | 8 |

**注意事項**
- 月間発行数が999件を超える種別は桁数拡張を検討すること
- 採番時は同時アクセスによる重複を防ぐため、DBトランザクション/ユニーク制約でのロック処理を実装すること
- IDに日付・種別情報が含まれるため、外部公開URL等への露出は避ける

### 2.1 帳票番号（t.archive）専用ルール ★追加

`t.archive`（請求書・見積書等）は、上記の基本ルールとは異なる採番方式とする。

```
1YYMMNN
1:  帳票番号の固定識別子
YY: 年（下2桁）
MM: 月（2桁）
NN: 通し番号（2桁、月次リセット）
```

- `NN`は**帳票種別（請求書/見積書/領収書等）を問わず、システム全体で共有する連番**とし、月が替わるたびに`01`から再開する
- 月間発行数が99件を超える場合は桁数拡張を検討すること（従業員4名規模の運用では当面想定しにくいが、将来の拡張点として留意）
- 採番時のロック処理は他IDと同様に必須

## 3. 認証・セッション仕様

### 3.1 ログイン方式

| 方式 | 用途 | 利用可否条件 |
|---|---|---|
| ID/パスワード認証 | 通常ログイン（全機能アクセス可、権限に応じる） | 退職者も可 |
| 社員証QRコード認証 | 勤怠打刻機能専用（第二フェーズ以降実装） | **退職者は禁止** |

**ログイン識別子**
- ID/パスワード認証時の識別子は、**「ログイン用ID（user_id）」または「電話番号」のいずれか**を入力する方式とする
- `user_id`は**NULL許可**とする。アカウント作成直後は`user_id`が未設定（NULL）の状態であり、**初回ログインは電話番号（プライマリ携帯番号）で行う**
- `user_id`を設定済みの場合は、**ログイン用ID（user_id）を主たる識別子（プライマリ）とし、電話番号は代替手段（サブ）として提供する**。ログイン画面のUIでもID入力欄を主要な導線とし、電話番号ログインは補助的な選択肢として配置する
- 電話番号での照合は、`t.address`（`address_user_code`で紐づく本人レコード）配下の`t.address_tel`のうち、**プライマリ（sort=1、従業員は携帯番号で固定）のレコードのみを照合対象とする**
- `user_id`は本人・管理者ともに**任意のタイミングで**管理画面から変更・設定できる（強制的な設定タイミングは設けない）。一意性制約はNULLを除いて維持する。変更履歴（旧ID）を`t.logs`に残すことを推奨する
- **他テーブルから`t.users`への参照は、`user_id`ではなく`user_code`（uid、TT=9）に統一する**（`user_id`はログイン専用の可変値であり、リレーションのキーとしては使用しない）

### 3.2 パスワードポリシー
- ハッシュ化アルゴリズム: **bcrypt**
- 最低文字数: **4文字以上**（高齢の従業員も利用するため、複雑性要件は設けず意図的に緩めの基準とする）
- **初回ログインのフロー**: `user_id`はアカウント作成時点でNULLのため、**初回ログインは電話番号（プライマリ携帯番号）＋初期パスワード（生年月日8桁）で行う**
  - **パスワードの再設定は、管理ユーザーを含む全アカウントが初回ログイン時に必須**とする。再設定が完了するまで他機能へのアクセスを許可しない
  - `user_id`の設定・変更は必須ではなく、**本人が任意のタイミング**で管理画面から行える

### 3.3 ロックアウト仕様
- ログイン失敗回数が `t.system.login_lockout_count`（デフォルト10回）に達するとアカウントを一時ロック
- **QRログインの失敗もパスワードログインと同一カウント**（`user_login_fail_count`）で管理する
- ロック解除は **管理者による手動操作のみ**。ユーザー管理画面から対象アカウントのロックを解除する操作を提供する（時間経過による自動解除は行わない）

### 3.4 QRコードログイン仕様
- 社員証に印字/表示されたQRコードから`user_auth_key`を読み取り、サーバー側で照合してログイン
- `user_auth_key`は暗号化してDB保存
- ログイン成功時、`session_mode = 2`（QR限定モード）でセッションを発行
- QR限定モードのセッションは**勤怠打刻機能のみアクセス可能**（ミドルウェアでホワイトリスト制御）
- `user_type = 9`（退職）の場合、`user_auth_key`が一致してもログインを拒否する

### 3.5 セッション管理
- **DBセッション方式**を採用（JWTは使用しない）
- NextAuthのAdapter機能（Prisma Adapter等）を利用し、`t.sessions`相当のテーブルで管理
- セッションには`session_mode`（通常/QR限定）を保持し、認可判定に利用

## 4. 権限管理仕様（RBAC）

### 4.1 基本方針
- `user_type`単位で、機能ごとの「閲覧・追加・編集・削除」可否をデータで管理する
- コード変更なしに権限設定を変更できる構成とする
- 将来的に個人単位の例外権限が必要になった場合は、上書き用テーブルを別途追加拡張する想定（本フェーズ対象外）

### 4.2 退職者の権限
- `user_type = 9`（退職）用の権限レコードを用意し、許可する機能のみ`can_view`等をtrueに設定
- ログイン自体は可能、利用可能機能は権限テーブルで制御

### 4.3 QR限定モードとの関係
- QR限定モード（`session_mode = 2`）は、権限テーブルとは別軸のアクセス制御
- 実際にアクセス許可される機能は、**「権限テーブルによる許可」AND「セッションモードによる許可」** の論理積で決定する

### 4.4 Rails実装方針
- 認可ロジックはPundit等の認可gemを用いて宣言的に実装する
- `t.role_permissions`の内容をベースに、Policyクラス側で`can_view` / `can_create` / `can_update` / `can_delete`を判定する構成とする

### 5.1 t.users（従業員）

| カラム名 | 型/備考 |
|---|---|
| user_code | uid（TT=9）主キー |
| user_id | ログイン用ID（**NULL許可**。本人・管理者が任意のタイミングで設定・変更可能） |
| user_type | enum: 1.システム管理者 / 2.管理職 / 3.事務職 / 4.一般 / 5.非常勤 / 9.退職 |
| user_pass | bcryptハッシュ |
| user_must_change_password | TF（初回ログイン時のパスワード変更要否） |
| user_familyname / user_firstname | 氏名（漢字） |
| user_familyname_ruby / user_firstname_ruby | 氏名（ふりがな・ひらがな） |
| user_birth | 誕生日 |

| user_join_date | 入社日 |
| user_login_fail_count | ログイン失敗回数（パスワード・QR共通カウント） |
| user_is_locked | ロック状態フラグ（管理者操作でのみ解除） |
| user_entry_date | システム登録日 |
| user_update_date | 更新日 |
| deleted_at | 論理削除日時（NULL許可） |

**備考**
- メールアドレス・電話番号は保持しない。`t.address`（`address_user_code`で紐づく）側で一元管理する
- 退職時は`user_type`を`9`に変更する運用（論理削除とは独立した状態管理）
- `user_id`は**NULL許可**。作成直後は未設定で、本人・管理者が**任意のタイミング**で管理画面から設定・変更できる（強制するタイミングは設けない）。設定済みの場合、ログイン用IDは電話番号ログインより優先されるプライマリな識別子となる
- **初回ログインは電話番号（プライマリ携帯番号）＋初期パスワード（生年月日8桁、YYYYMMDD形式）で行う**。パスワードの再設定は管理ユーザーを含む全アカウントで初回ログイン時に必須とし、`user_must_change_password = true`の間は再設定画面以外へのアクセスを制限する
- **他テーブルから`t.users`を参照する際のキーは`user_code`に統一する**（`user_id`はリレーションに使用しない）

### 5.4 t.address_tel（電話番号）★新規

| カラム名 | 型/備考 |
|---|---|
| at_id | 主キー |
| address_id | t.address への外部キー |
| at_number | 電話番号 |
| at_label_type | ラベル種別 enum: 1.携帯 / 2.代表 / 3.FAX / 4.自宅 / 5.緊急連絡先 / 6.自由入力 |
| at_label_free | 自由入力ラベル（`at_label_type = 6` の場合のみ使用、NULL許可） |
| at_sort | 表示順（**sort=1のレコードをプライマリとして扱う**） |

**ラベル仕様**
- 「携帯・代表・FAX・自宅」は固定値としてマスタ管理する（`at_label_type`の1〜4）。フロントの入力UIでは選択式とする
- 上記4種以外を入力したい場合は`at_label_type = 6（自由入力）`を選択し、`at_label_free`にテキストを入力する
- **緊急連絡先（`at_label_type = 5`）は、従業員本人のアドレス（`address.address_user_code`が非NULLのレコード）に限り使用可能とする**。取引先等（`address_user_code`がNULL）のアドレスには付与できない
- 緊急連絡先は**1つのアドレスにつき1件まで**とする（同一`address_id`内で`at_label_type = 5`を複数登録することはできない）。単純な`UNIQUE(address_id, at_label_type)`は他のラベル種別（携帯・代表等）の複数登録も妨げてしまうため不適切。アプリケーション側でのバリデーションに加えて、DB側で担保する場合は`at_label_type = 5`の行にのみ非NULLとなる生成列（例: `emergency_flag`）を追加し、`UNIQUE(address_id, emergency_flag)`とする（MariaDBのユニークインデックスはNULLを複数許容するため、他のラベル種別には影響しない）
- **従業員のプライマリ（sort=1）は「携帯」で固定する運用**とする（`at_label_type = 1`を第一連絡先として登録する）。プライマリ変更時にも携帯番号がsort=1を維持するよう、フロント側の並び替えUIで制御する

## 6. アドレス帳検索仕様

- **実装場所**: フロントエンド（Next.js側）で実施。少人数運用（従業員4名程度＋取引先）のため全件取得の上でクライアント側フィルタリングとする
- **検索対象項目**（いずれかに部分一致した場合ヒット）:
  1. `address_ruby`（ひらがな）
  2. カタカナ変換した`address_ruby`（フロント側で入力値をひらがな/カタカナ双方に正規化して比較）
  3. `address_name`（漢字）
  4. `address_tel.at_number`（複数件）
  5. `address_email.ae_email`（複数件）
  6. `address_contact_name`（担当者名）
- **データ取得**: APIレスポンスは`t.address`に`t.address_tel` / `t.address_email`をJOINした形で返却し、フロント側で保持・検索する

## 9. ファイルストレージ構成

### 9.1 選定ツール：SFTPGo
- ライセンス：AGPLv3（無料）
- S3互換API・SFTP・FTP・WebDAV対応の高機能ファイルサーバー
- MinIOはコミュニティ版の機能制限（ライセンス変更）リスクがあるため不採用。SFTPGoはこのリスクが現状低く、長期運用前提の自宅サーバーに適する
- Rails側からはS3互換APIとして扱うため、`aws-sdk-s3` gem等の標準的なライブラリで実装可能

### 9.2 構成イメージ
```
[Rails API] --S3互換API--> [SFTPGo コンテナ] --> ローカルディスク（TX1310 M3側）
```
- `t.files.file_path` には SFTPGo内でのオブジェクトキー（パス）を保存する
- バックアップは、SFTPGoが使用するディスク領域を N100ミニPC側へ resticまたはrsyncで定期同期する

### 9.3 フォルダ構成（電子帳簿保存法対応）

第一フェーズの対象ではないが、`t.archive`（請求書・見積書等）と一般ファイル（資格証明書等）を**同一のSFTPGoコンテナ**で管理する方針のため、法令要件を踏まえたフォルダ分離設計を以下の通り定める。

```
[SFTPGoコンテナ]
 ├─ /files/general/      通常ファイル（資格証明書 等）
 │                        → 上書き・削除 可（論理削除はRails側で管理）
 └─ /files/archive/       帳票ファイル（請求書・見積書 等）
                          → 作成のみ可、上書き・削除 不可（WORM運用）
```

**真実性確保の方式**
電子帳簿保存法が求める「真実性の確保」について、有料のタイムスタンプ局サービスを使わず、以下の方式で対応する。
- `/files/archive/` フォルダに対しては、アプリケーション用SFTPGoユーザーの権限を「作成のみ許可、上書き・削除不可」に設定する
- 内容の訂正が必要な場合は、元ファイルを削除せず新バージョンとして別ファイルを保存し、`t.archive`側で新旧の履歴を管理する
- すべてのファイル操作を`t.logs`（`log_target_table` / `log_target_id`）に記録する

**フォルダ振り分けロジック**
- `t.files.file_type` の値に応じて、アップロード先フォルダ（`/files/general/` または `/files/archive/`）をRails側のアップロード処理で自動判定する
- 保存期間（原則7年、欠損金がある場合は最大10年）経過後の削除は、アプリケーションからの明示的な削除操作のみで行う。`/files/archive/` に対する通常の削除権限はSFTPGo側で付与しない

### 9.4 バックアップ運用上の注意
- N100ミニPCへの同期にresticを使用する場合、スナップショット機能により過去バージョンも保持されるため、バックアップ側でも実質的にWORM運用を維持できる
- 7〜10年という長期保存が前提のため、SFTPGoコンテナ自体の更新・移行時にも本フォルダ構成・権限設定を引き継ぐ運用ルールをドキュメント化しておくこと

### 9.5 本フェーズでの対応範囲
- 第一フェーズ（ログイン・従業員管理・アドレス帳）では `/files/general/` のみ使用（資格証明書等は第二フェーズ以降の対象だが、フォルダ構成自体は先行して用意しておく）
- `/files/archive/` の権限設定・運用は `t.archive` 実装フェーズ（第四フェーズ想定）着手前に確定させること

## 10. システム・自社情報管理（t.system）

### 10.1 概要
プロダクトロゴ・自社情報・振込先情報等、システム全体で参照する設定情報を一元管理する。**シングルトンテーブル**（常に1レコードのみ）として設計する。

- ロゴ・ファビコン・コーポレートロゴ・印影等のファイルは、既存の`t.files`を流用し`file_id`で紐づける
- アプリケーション側で「id=1のレコードのみ更新可能」という制約を実装し、複数レコードが作られる事故を防ぐこと
- 振込先口座・消費税率など、変更した際に影響が大きい項目については、`t.logs`とは別に変更前後の値を残す運用も将来的に検討する

### 10.2 テーブル定義

| カラム名 | 型/備考 |
|---|---|
| system_id | 主キー（常に1固定） |
| system_name | システム名称 |
| system_logo_file_id | システムロゴ（t.files 紐付け） |
| system_favicon_file_id | システムファビコン（t.files 紐付け） |
| company_name | 会社名 |

| company_address | 所在地 |
| company_tel | 電話番号 |
| company_email | メールアドレス |
| company_invoice_number | 適格請求書発行事業者登録番号（インボイス番号） |
| company_corporate_number | 法人番号 |
| representative_position | 代表者役職 |
| representative_name | 代表者名 |
| corporate_logo_file_id | コーポレートロゴ（t.files 紐付け） |
| corporate_logotype_file_id | コーポレートロゴタイプ（t.files 紐付け） |

### 10.3 運用ルールの補足

- **消費税端数処理**：四捨五入で固定とする（設定項目化せず、アプリケーションロジックに固定値として実装する）
- **login_lockout_count**：現行仕様の「10回」をハードコードせず、本テーブルの値を参照する形に変更する。第3章（認証・セッション仕様）のロックアウト処理は、この値を参照するよう実装すること
- **fiscal_year_end_month**：決算月を登録できるようにする（開始月ではなく終了月で管理）。年次集計・帳票保存年数の起算等、第二フェーズ以降の機能で参照する想定
- **default_tax_rate**：請求書・見積書作成時の初期値として使用。税率変更時の履歴管理（将来の`t.tax_rates`等）は本フェーズの対象外

## 11. フロントエンド実装方針

### 11.1 技術スタック
- **Next.js + Tailwind CSS**
- **PWA対応**：manifest.json、Service Workerを実装し、スマートフォンのホーム画面への追加を可能にする。特にQRコードログイン（社員証読取）はスマートフォンでの利用が想定されるため、PWA化によりアプリライクな導線を用意する
- **UIコンポーネント**：Tailwindベースのコンポーネントライブラリ（例：shadcn/ui）の利用を推奨。フォーム・モーダル・トースト等の基本部品をゼロから実装しない

### 11.2 デザイン方針

**配色**
- ベースカラー：シックなグレー系
- アクセント/ブランドカラー：コーポレートロゴに合わせた緑系（`tailwind.config`にカスタムカラーとして定義する）

**レスポンシブ対応**
- **デスクトップファーストで実装する**。まずPC幅を基準にレイアウトを組み、モバイル対応は後続タスクとしてブレークポイント別のスタイル調整（`sm:` `md:`等のTailwindユーティリティ）で対応する
- 一覧画面（従業員一覧・アドレス帳一覧）は、PC幅ではテーブル表示、モバイル対応時にはカード型リストへの切り替えを想定し、コンポーネント構造をあらかじめ分離しておく

**アクセシビリティ・高齢者対応**
- 本文の基準フォントサイズは大きめに設定する（16px以上を基準とし、本文相当は18px程度を目安とする）
- コントラスト比を確保する（WCAG AA相当を目安）
- アイコンのみに頼らず、主要な操作ボタンにはテキストラベルを併記する

**タッチ操作への配慮**
- タップ対象（ボタン・リンク・チェックボックス等）は最低44px四方のタップ領域を確保する
- QRコードスキャン画面など、スマートフォンでの操作が中心となる画面は特に余白・ボタンサイズに配慮する

### 11.3 フォーム実装
- `react-hook-form` + `zod` の組み合わせで統一する
- バリデーションルール（パスワード4文字以上、電話番号フォーマット等）はzodスキーマとして一元管理し、フロントエンドでの入力チェックとバックエンド側のチェック内容の整合性を保つ

## 12. 開発環境・リポジトリ構成

### 12.1 リポジトリ構成
- **単一リポジトリ（モノレポ）** とし、ディレクトリでフロントエンド/バックエンドを分割する

```
/repo-root
 ├─ frontend/    Next.js（Tailwind CSS, PWA設定を含む）
 ├─ backend/     Ruby on Rails（API）
 ├─ docker/      Docker Compose定義、各種コンテナ設定
 └─ docs/        本仕様書含むドキュメント類
```

### 12.2 ローカル開発環境
- 本番環境（Proxmox上のDockerコンテナ：Next.js／Rails／MariaDB／SFTPGo）と同一構成をDocker Composeでローカル再現する
- **`frontend/`・`backend/`それぞれにMakefileを用意し、環境構築・起動・テスト実行等の操作を統一されたコマンドで行えるようにする**

**frontend/Makefile に用意するコマンド例**
```
make setup     # 依存パッケージインストール
make dev       # 開発サーバー起動
make lint      # ESLint / Prettier チェック
make test      # フロントエンドテスト実行
make build     # 本番ビルド
```

**backend/Makefile に用意するコマンド例**
```
make setup     # bundle install、DBセットアップ
make dev       # Railsサーバー起動
make db-migrate    # マイグレーション実行
make db-seed       # シード投入（管理ユーザーのみ、詳細は13章）
make lint      # RuboCop チェック
make test      # RSpec実行
```

- ルート直下にも `make up`（Docker Compose全体起動）等の統合コマンドを用意し、初回セットアップの手順を最小限にする

### 12.3 コーディング規約

**フロントエンド（Next.js）**
- ESLint + Prettier を導入し、コミット前フォーマットを統一する
- コンポーネントは機能単位（`features/`）で分割し、共通UIパーツは`components/ui/`に配置する
- 命名規則：コンポーネント・ファイル名はパスカルケース（`EmployeeList.tsx`）、変数・関数はキャメルケース

**バックエンド（Rails）**
- RuboCop を導入し、Rails標準の規約（Rails Style Guide相当）に準拠する
- テーブル・カラム名はスネークケース（本仕様書のテーブル定義に準拠）
- APIエンドポイントはRESTfulな設計を基本とし、`/api/v1/`配下にバージョニングする

**共通**
- コミットメッセージの書式（例：Conventional Commits）を統一する
- 本仕様書のテーブル定義・カラム名は実装時の正としてそのまま使用し、変更が生じた場合は本ドキュメントを都度更新する

### 12.4 テスト方針
- **最低限のテストを実装する**。優先度が高い領域は以下の通り
  - **認証・ロックアウト・初回ログイン強制**（Rails: RSpecでの単体・リクエストテスト）
  - **論理削除の挙動**（削除後にレコードが一覧に表示されないこと、退職者のアドレス帳表示継続等）
  - **権限チェック（RBAC）**（`user_type`ごとのアクセス可否）
  - **フロントエンドの主要フォーム**（ログイン画面、従業員登録・編集フォーム、アドレス帳登録・編集フォームの入力バリデーション）
- E2Eテスト（Playwright等）は本フェーズでは必須とせず、余力があれば主要導線（ログイン→初回ID/パスワード再設定→ダッシュボード表示）のみカバーする

## 13. 初期データ・シード方針

### 13.1 管理ユーザーの固定シード
- マイグレーション／シード投入時、**管理ユーザー（`user_type = 1`）のみを固定データとして1件作成する**。他のマスタデータ（`address_category`等）は前述の通り初期データなしとする
- 固定作成する管理ユーザーの初期値：

| カラム | 値 |
|---|---|
| user_code | システム採番（TT=9の最初の番号） |
| user_id | **NULL**（未設定。本人が任意のタイミングで設定） |
| user_type | 1（システム管理者） |
| user_pass | 生年月日8桁を初期パスワードとして設定（bcryptハッシュ化） |
| user_must_change_password | true |

**注意事項**
- ログインは電話番号ベースで行うため、シード投入時に管理ユーザーの`user_code`と紐づく`t.address`レコード（`address_user_code`）、および携帯番号を`at_label_type = 1`・`at_sort = 1`（プライマリ）として登録した`t.address_tel`レコードもあわせて作成する必要がある
- 実運用の電話番号が未確定な段階でシードを流す場合は、初期セットアップ時に管理者が管理画面から実際の携帯番号を登録するまでログインできない点に留意する

### 13.2 初回ログイン時の必須設定
- **管理ユーザーを含む全アカウント**が対象
- **初回ログインは電話番号（プライマリ携帯番号）＋初期パスワード（生年月日8桁）で行う**（`user_id`は未設定のため使用しない）
- 初回ログイン成功後、専用画面で**パスワードの再設定を強制**する。再設定が完了するまで他機能（従業員管理・アドレス帳等）へのアクセスを許可しない
- `user_id`の設定・変更は必須ではなく、**本人が任意のタイミング**で管理画面から行える
- パスワード再設定完了後、`user_must_change_password`を`false`に更新する

## 14. Claude Code実装引き継ぎ方針

### 14.1 前提
- GitHubリポジトリ：**作成済み（public）**
- 本仕様書（`docs/ERP_phase1_spec.md`）をリポジトリ内に配置し、Claude Code（VS Code拡張）に読み込ませた上でIssue作成・実装を依頼する
- Claude CodeからのIssue作成には、GitHub MCPサーバー接続（`claude mcp add`によるPersonal Access Token設定）が必要

### 14.2 ブランチ戦略
- **featureブランチ + PRマージ方式**を採用する
- 命名規則：`feature/<issue番号>-<概要>`（例：`feature/12-auth-login`）
- 各Issueの実装は個別のfeatureブランチで行い、完了後にmainブランチへのPull Requestを作成する
- PRの説明文には、対応するIssue番号・実装内容の要約・動作確認方法を含める
- レビュー後にmainへマージする運用とし、mainへの直接コミットは行わない

### 14.3 Issue分割方針（章単位）
Issueは機能・章単位で分割する。以下を目安として、Claude Codeに作成を依頼する。

| # | Issueタイトル（例） | 対応する仕様書の章 | 概要 |
|---|---|---|---|
| 1 | 開発環境構築 | 12章 | モノレポ構成（frontend/backend/docker/docs）、Docker Compose、各Makefile、コーディング規約設定（ESLint/Prettier、RuboCop） |
| 2 | DBスキーマ・マイグレーション | 5章、10章、13章 | t.users、t.address関連、t.system等のマイグレーション作成、管理ユーザーの固定シード投入 |
| 3 | 認証機能 | 3章 | ID/電話番号ログイン、bcrypt、ロックアウト、DBセッション管理、QR限定モードの基盤、初回ログイン時のパスワード再設定フロー |
